# Gate Validation Technical Context

## Public surface

- `POST /api/scanner/qr-data` accepts QR ciphertext, station ID, and gate; it returns success or a bad-request message. No explicit `[Authorize]` is present on the inspected controller.
- Gate values currently use `Entry` and `Exit`. Keep casing/normalization behavior compatible unless contract changes are accepted.

## Code map

- API: `SmartMetroService.Api/Controllers/ScannerController.cs`.
- Logic: `SmartMetroService.Application/Managers/ScannerService.cs`, `TicketService`, `StationService`, `WalletService`.
- Persistence/cache: ticket, rapidpass, journey, station, wallet repositories; `IDistributedCache` for RapidPass entry state.
- QR format: encrypted serialized `QrPayload` generated by ticketing service.

## Design risks to resolve

Current RapidPass cache key is the pass ID and a successful exit removes it; concurrent entry/exit, duplicate scans, cache expiry, and fare debit/journey persistence need atomicity/idempotency design. Current single-ticket path transitions ticket state in multiple database writes. Confirm device identity and whether scanner errors may disclose internal exception messages before altering the API.
